# PM209 RAG 핵심 정리 — 청킹·임베딩부터 검색·답변까지

2026-11-02 수정본. 앞서 보낸 짧은 요약에 빠졌던 청킹·임베딩 방법과 설정 이유를 보완했습니다. 실제 코드와 완료 기록을 기준으로 정리했습니다.

## 1. 현재 어디까지 했는가

**209개 매뉴얼·10,018페이지를 126,938개 청크로 나누고, GPU 임베딩과 Qdrant 저장을 완료했습니다. 이후 LangChain으로 질문 번역→검색→한국어 답변을 연결하고, 30문항으로 가중치·Top-k 비교까지 진행했습니다.**

| 단계 | 실제 처리 | 담당 |
|---|---|---|
| ① 입력 준비 | 기존 본문 OCR·그림 description·표 HTML 사용 | 기존 문서 분석 결과 |
| ② 청킹 | 본문·그림 설명·표를 검색에 쓸 텍스트 단위로 분리 | 직접 작성한 Python 청킹 코드 |
| ③ 임베딩 | 청크 텍스트를 1,024차원 의미 벡터로 변환 | Qwen3-Embedding + Ollama |
| ④ 저장·검색 | 벡터·본문·출처 저장, 의미·키워드 검색 및 순위 결합 | Qdrant |
| ⑤ 답변 | 질문 번역, 검색 근거를 이용한 한국어 답변과 출처 연결 | LangChain + Qwen3.5 |

②~④의 문서 준비는 미리 수행합니다. 사용자가 질문하면 질문만 번역·임베딩한 뒤 기존 DB를 검색합니다. **청킹만 실행한다고 임베딩·DB 저장이 자동으로 되는 것은 아니며**, 전체 실행기가 이 단계를 차례로 연결했습니다.

## 2. 청킹은 어떻게 했는가

### 기본 단위와 500자 기준

- 기본 상한은 **500자**입니다. 토큰 수가 아니라 공백·제목·반복되는 표 헤더까지 포함한 문자열 길이입니다.
- 같은 매뉴얼·페이지 안에서, 같은 제목과 열에 속하고 가까이 있는 본문을 먼저 묶습니다. 페이지가 바뀌거나 제목·열이 달라지면 합치지 않습니다. 제목과 열의 연결은 기존 좌표를 이용한 규칙입니다.
- 묶은 본문을 문장 경계로 구분하고, **500자 안에 들어가는 인접 문장들을 순서대로 한 청크에 담습니다.** 청크가 무조건 한 문장인 것은 아닙니다. 제목도 검색 문맥으로 붙이며 길이에 포함합니다.

500자는 작은 단위로 필요한 내용을 찾으면서 인접 문맥도 담기 위한 초기 기준입니다. 너무 긴 청크에 여러 주제가 섞이거나, 너무 짧게 나눠 조건·설명이 떨어지는 문제를 줄이려는 선택입니다. **500자가 최적이라는 비교 실험을 끝낸 것은 아닙니다.**

### 긴 문장 분할·합치기·겹침

1. 마침표·물음표·느낌표 등의 **문장 경계**를 우선합니다. 소수점과 일부 약어·번호 표기는 일반 문장 끝과 구분합니다.
2. 문장 하나가 남은 길이보다 길고 통째로 담을 수 없으면, 쉼표·세미콜론·콜론 같은 **구절 경계**를 먼저 찾고, 적절한 경계가 없으면 **공백 기준 단어 경계**에서 나눕니다.
3. 일반 분할에서는 앞 청크의 마지막 완전한 문장이 **100자 이하일 때** 다음 청크에 반복합니다. 긴 문장을 나눈 경우에는 끝부분을 단어 경계에 맞춰 **최대 100자** 겹칩니다.
4. 겹침 때문에 다음의 온전한 문장을 다시 쪼개야 한다면 겹침을 생략합니다. 따라서 모든 청크에 정확히 100자가 반복되는 것은 아닙니다.

예를 들어 제목 길이를 제외한 설명용 예시에서 A가 약 300자, B가 80자, C가 250자라면 `청크 1 = A+B`, `청크 2 = B+C`처럼 만들 수 있습니다. B를 반복하면 경계에서 문맥이 끊기는 것을 줄일 수 있습니다. 나눈 모든 조각을 마지막에 다시 하나로 합치지는 않습니다. 검색할 때 선택된 청크들이 답변 근거로 함께 전달됩니다.

공백 없는 긴 식별자나 지나치게 긴 제목·표 문맥은 억지로 잘라 버리지 않고 예외로 남깁니다. 실제 **500자 초과 청크는 26개**, 모두 긴 표 문맥 예외였고 최대 1,776자였습니다. 검수 표시를 붙였으며, 단어 경계 분할만으로 모든 숫자·단위·절차의 의미 연결까지 보장하지는 않습니다.

### 본문·그림·표는 각각 어떻게 처리했는가

| 유형 | 청킹 방식과 문맥 유지 |
|---|---|
| 본문 | 같은 제목·열의 가까운 본문을 묶고 문장 단위로 채웁니다. 긴 문장은 위 규칙으로 분할합니다. 원문 번호와 순서는 유지하되 절차의 전제 조건을 의미적으로 추론해 추가하지는 않습니다. |
| 그림 | **이미지 파일이 아니라 기존 description 텍스트**를 청킹합니다. 그림별로 독립 처리하고, 길면 500자 기준으로 나눕니다. 원래 그림 ID·페이지 이미지 경로·좌표를 연결합니다. |
| 표 | 기존 HTML을 파싱해 `열 이름: 셀 값` 형태의 검색 텍스트를 만듭니다. 긴 표는 행 단위, 긴 행은 셀 단위로 나누고, 필요한 헤더·첫 셀의 행 이름·제목 등을 반복합니다. 표에는 앞 행을 100자씩 겹치는 규칙을 적용하지 않습니다. |

표의 병합 셀은 원래 셀을 참조하도록 펼쳐 행·열 연결을 유지합니다. 명시된 헤더는 열 이름으로 사용하지만, 헤더가 불명확하면 첫 행을 임의로 확정하지 않습니다. 구조가 맞지 않는 표는 셀 문자를 순서대로 보존하고 `table_structure_unresolved`로 표시합니다. **원래 HTML은 수정하지 않습니다.** 수기 요약 표 12개도 별도 검수 표시를 유지합니다.

청크에는 `chunk_id`, 매뉴얼·페이지·영역 ID, 유형, 이미지 경로, 좌표, 제목, 원문 문자 범위 또는 표 행·셀 참조, 검수 표시를 저장합니다. 검색한 문장을 원래 문서 위치로 되짚기 위한 정보입니다. **QA 질문·정답은 청킹 입력에서 제외했습니다.**

최종 청크는 **본문 85,849 + 그림 26,546 + 표 7,624 + 제목 6,919 = 126,938개**입니다. 그림 23,807개와 표 2,320개의 연결을 확인했습니다. 하나의 그림·표가 여러 청크가 될 수 있어 원본 객체 수와 청크 수는 다릅니다.

## 3. 임베딩은 어떻게 했는가

### 텍스트를 벡터로 변환

각 청크의 `text`를 **`qwen3-embedding:0.6b`**에 넣어 **1,024개의 숫자로 된 의미 벡터**를 만들었습니다. 텍스트에 이미 붙인 제목·표 헤더는 함께 임베딩하지만 ID·좌표·QA는 임베딩 본문에 넣지 않습니다. 이들은 출처 메타데이터로 따로 저장합니다.

그림은 description, 표는 HTML에서 변환한 행·셀 텍스트를 임베딩했습니다. **원본 이미지 픽셀을 직접 임베딩한 구성은 아닙니다.** 모델을 추가 학습하거나 가중치를 수정하지 않고, 설치된 모델로 벡터를 생성했습니다.

| 항목 | 실제 설정 |
|---|---|
| 모델·양자화 | `qwen3-embedding:0.6b`, Q8_0 |
| 벡터 차원 | 1,024 |
| GPU | RTX 5060 Laptop, VRAM 8,151MiB |
| 요청 배치·동시성 | 한 요청에 청크 4개, 요청 1개씩 순차 처리 |
| 문맥·잘림 처리 | 문맥 2,048토큰, `truncate=false`; 2,000토큰 초과 입력은 사전 검토 대상으로 차단 |
| 내부 처리 설정 | `num_batch=128`, CPU 스레드 4 — 청크 4개 요청 배치와는 다른 설정 |
| 실제 입력 길이 | 전체 청크의 최대 측정 길이 500토큰; 500자와는 별도 측정값 |

0.6B 모델과 작은 배치로 로컬 8GB GPU에 맞췄습니다. 실제 실행 가능성과 자원 사용을 확인한 선택이며, 여러 임베딩 모델 중 정확도 1위라는 뜻은 아닙니다. 그림 설명 생성 때 사용했던 768 출력 토큰 제한은 임베딩에 적용하지 않습니다.

**문서와 질문은 같은 임베딩 모델·차원·설정을 사용합니다.** 문서에는 별도 질문 지시문을 붙이지 않고, 질문에는 다음 검색 지시문을 붙입니다. 현재는 영어 문서 검색을 위해 한국어 질문을 영어로 번역한 뒤 이 형식으로 임베딩합니다.

```text
Instruct: Given a question about a product manual, retrieve passages that answer the question.
Query: <검색할 질문>
```

답변 모델은 다른 모델이어도 됩니다. 질문과 문서를 비교할 벡터 공간을 만드는 모델과, 찾은 근거를 읽고 답을 쓰는 모델의 역할이 다르기 때문입니다.

### SQLite가 들어간 이유와 재사용

`embedding-cache.sqlite3`는 **이미 생성한 벡터를 다시 계산하지 않도록 보관하는 캐시**입니다. 입력 텍스트·모델 digest·설정·문서/질문 용도를 구분하고, 배치마다 저장해 중단 후 재개와 중복 계산 방지에 사용했습니다.

2026-10-26 전체 실행에서는 **112,067개를 새로 생성하고 14,871개는 캐시에서 재사용**했습니다. 임베딩 단계는 약 **90.2분**, 최초 Qdrant 적재는 약 **15.2분**이었고, 청킹·검증까지 전체 약 **1시간 51분**이었습니다. 당시 임베딩 GPU 관측 최대는 약 1,016MiB·67°C였습니다.

이번 LangChain·Qdrant 전환에서는 **기존 126,938개 문서 의미 벡터를 전부 재사용**했습니다. 현재 경로는 기존 SQLite 캐시를 읽기 전용으로 사용하고 새 질문 벡터는 JSON 캐시에 저장합니다. 이전 실험의 SQLite FTS 키워드 검색은 기록으로 남아 있지만, **현재 키워드 검색은 Qdrant에서 수행합니다.**

## 4. Qdrant에는 무엇을 넣고 어떻게 검색하는가

현재 컬렉션은 `pm209_hybrid_v1`입니다. 청크마다 동일한 ID에 다음을 연결했습니다.

- **dense**: Qwen이 만든 1,024차원 의미 벡터. Qdrant가 코사인 유사도로 비교합니다.
- **bm25**: `FastEmbedSparse(Qdrant/bm25)`가 만든 키워드 희소 벡터. Qdrant의 IDF 처리를 함께 사용합니다.
- **payload**: 청크 텍스트와 매뉴얼·페이지·원본 영역 ID·좌표·유형 등 출처 정보입니다.

Qdrant는 **로컬 디스크 모드**로 사용하므로 별도 서버나 Docker를 띄우지 않았습니다. 같은 DB 경로를 여러 프로세스가 동시에 여는 서비스 구성은 아직 아닙니다.

검색은 지정한 매뉴얼로 범위를 제한한 다음 의미 검색과 키워드 검색의 후보를 각각 최대 20개 얻고, **Qdrant 내부 가중 RRF**로 순위를 결합합니다. `키워드 0%`는 의미 검색만, `100%`는 키워드 검색만 사용합니다. 중간 값은 두 검색 순위의 결합 비중이며, 모델 가중치나 답변 개수를 조절하는 값이 아닙니다. 설정을 바꿀 때 문서 임베딩을 다시 만들 필요도 없습니다.

현재 실행 기본값은 **키워드 50%·Top-5**, RRF 상수는 60입니다. **Top-1은 근거 청크 1개, Top-5는 최대 5개를 읽고 각각 답변 하나를 생성한다는 뜻**입니다. 기본값 50%를 최적값으로 확정한 것은 아닙니다.

## 5. LangChain과 답변 LLM은 어떻게 연결했는가

```text
한국어 질문
 → Qwen3.5로 영어 번역
 → 같은 Qwen 임베딩 모델 + BM25 질문 벡터
 → Qdrant 매뉴얼 필터·검색·가중 RRF·Top-k
 → 원래 한국어 질문 + 검색된 근거 텍스트
 → Qwen3.5의 한국어 답변 + 근거 ID 검증
```

LangChain의 `RunnableSequence`, `ChatPromptTemplate`, `ChatOllama`, 임베딩 어댑터, `QdrantVectorStore`로 이 실행 흐름을 연결했습니다. **청킹 규칙은 기존 직접 작성한 Python 코드**이며 LangChain TextSplitter로 바꾼 것은 아닙니다. LangChain은 각 도구를 연결하는 프레임워크이고, 그 자체가 OCR 오류나 답변 정확도를 자동으로 해결하지는 않습니다.

번역·답변 모델은 **`qwen3.5:4b` Q4_K_M**입니다. 답변은 `think=false`, temperature 0, 문맥 8,192토큰, 출력 최대 1,024토큰, 요청 제한 300초로 실행합니다. 8GB GPU에서 질문 임베딩 후 임베딩 모델을 내리고 답변 모델을 사용하도록 순차 처리합니다.

모델에는 원래 질문과 검색 청크의 텍스트·유형·검수 표시·`S1` 같은 근거 ID를 줍니다. **평가용 정답이나 원본 이미지 바이트는 넣지 않습니다.** 숫자·단위·조건을 보존하고, 근거가 부족하면 확인하지 못했다고 답하도록 프롬프트를 구성했습니다.

출력은 `answer`, `source_ids`, `insufficient_evidence`로 받습니다. 코드가 근거 ID를 실제 청크·페이지·좌표에 연결하고, 형식 오류는 한 번 재시도합니다. 출처가 유효하다고 내용까지 정확한 것은 아닙니다. 그림 좌표·경로는 보관하지만 실제 이미지 표시와 채팅 UI는 아직 구현하지 않았습니다.

## 6. 검증과 답변 비교 결과

전체 **126,938개 벡터·1,024차원·payload·기존 벡터 재사용**을 확인했고, 원본/그림/표 9개 JSONL을 포함한 보호 대상 482개 파일의 보존을 검증했습니다. 관련 검사 17개와 실제 검색·답변 명령도 통과했습니다. 이는 저장·연결 검증이며 모든 답변의 정확도 인증은 아닙니다.

같은 30문항(본문 10·표 10·그림 10)에 대해 키워드 비중 5개 × Top-1/5로 **답변 300개를 새로 생성**했습니다. 아래는 완전 정답 수이며 부분정답·미답변·형식 오류도 분모에 포함했습니다.

| 키워드 비중 | 전체 Top-1 /30 | 전체 Top-5 /30 | 본문 질문 Top-1 /10 | 본문 질문 Top-5 /10 |
|---|---:|---:|---:|---:|
| 0% | 15 | 20 | 8 | 9 |
| 25% | 13 | 18 | 6 | 9 |
| 50% | 14 | 18 | 7 | 9 |
| 75% | 14 | 18 | 7 | 8 |
| 100% | 10 | 16 | 4 | 7 |

이번 표본의 최고는 **키워드 0%·Top-5: 20/30개(66.7%)**였습니다. 유형별로는 본문 9/10, 표 6/10, 그림 5/10입니다. 본문 질문 집계도 검색 자료를 본문만으로 제한한 실험은 아닙니다.

표의 숫자·단위·조건 오역, 그림 설명의 위치·버튼 정보 부족, 여러 청크에 흩어진 긴 절차의 누락이 남았습니다. 출력 형식 오류는 **3/300개**로, 모두 근거 부족 표시와 출처 ID가 모순된 경우였습니다. 검수는 Codex가 수행했으며 독립적인 사람 평가나 새로운 질문에 대한 검증은 아닙니다. 이전 SQLite/Python 실험과는 BM25·가중 RRF 계산도 달라졌으므로 성능 차이를 LangChain만의 효과로 볼 수 없습니다.
