# PM209 RAG 프로젝트 진행 정리

작성일: 2026-11-09 · 2026-11-08까지의 코드와 실행·검수 기록 기준

## 1. 현재 어디까지 했는가

**문서의 그림·표 보강 → 청킹 → GPU 임베딩 → Qdrant 저장 → 검색 → 부모 문맥 연결 → 한국어 답변 생성까지 연결했습니다.** 같은 30문항으로 검색 가중치, Top-k, 부모 문맥, 답변 프롬프트를 비교했습니다.

| 항목 | 현재 상태 |
|---|---|
| 데이터 | PM209 제품 매뉴얼 209개, 10,018페이지 |
| 그림 | 23,807개에 설명 텍스트 추가 |
| 표 | 자동 추출·복구 2,308개 + 검색용 수기 보강 12개 |
| 청크·벡터 | 126,938개 청크, 1,024차원 의미 벡터 저장 |
| 사용 환경 | Windows 11, RTX 5060 Laptop, VRAM 약 8GB |
| 현재 실행 | 매뉴얼을 지정하고 질문하면 한국어 답변과 출처 반환 |
| 미구현 | 채팅 UI, 실제 그림 표시, 이미지 픽셀 기반 검색·답변 |

초기의 PP-StructureV3·PaddleOCR-VL 비교는 문서 분석 방식에 대한 선행 실험입니다. 현재 PM209에서는 **데이터셋이 제공하는 파싱 결과·좌표를 재사용**하고 그림과 표를 보강했습니다. 전체 문서를 PaddleOCR-VL로 다시 분석한 구성은 아닙니다.

## 2. 문서 데이터는 어떻게 준비했는가

- **본문·제목·좌표:** PM209의 기존 페이지 단위 JSONL을 사용했습니다.
- **그림:** 페이지 JPG의 기존 `shape` 좌표로 메모리에서 잘라 Qwen3.5-4B에 전달하고, 그림 객체에 영어 `description`을 추가했습니다. 재개 이후에는 2~4문장 중심으로 요청했으며 이전에 저장한 긴 설명도 유지했습니다.
- **표:** `structure == "Table"` 영역만 잘라 PaddleOCR의 **TableRecognitionPipelineV2**로 OCR 문자와 표 구조를 결합했습니다. 결과 HTML을 기존 객체의 `table_content`에 저장했습니다. 기존 위치를 활용해 레이아웃 분석·방향 분류·왜곡 보정은 껐습니다.
- **보존:** 원본 페이지·본문·ID·좌표·QA와 기존 그림 설명을 유지하고, 단계별 보강본을 별도로 저장했습니다. QA 정답은 보강·청킹·임베딩·답변 생성 입력에 넣지 않았습니다. 평가 질문은 실험 질의로만 사용했습니다.

주요 시행착오는 다음과 같습니다.

| 문제 | 대응과 남은 한계 |
|---|---|
| 그림 설명의 출력 길이 초과·토큰 반복으로 중단 | 간결한 설명 지침, 그림별 재시도, 실패 기록, 체크포인트·저장분 재사용으로 전체 완료 |
| Qwen의 HTML·Markdown 표 생성에서 반복·구조 오류 | 해당 실험 중단 후 OCR+표 구조 인식 파이프라인으로 전환. HTML 자체가 불가능하다는 의미는 아님 |
| Paddle 첫 순회에서 표 232개 제외 | 형식 검사와 실제 인식 오류를 분리. 208개는 내용을 유지한 HTML 보완, 24개만 재인식해 12개 채택 |
| 끝까지 자동 처리가 안 된 표 12개 | 원본을 참고한 검색용 수기 HTML을 별도 보강. 일부 요약·아이콘 누락이 있어 검수 표시 유지 |

**추출·저장 완료율과 내용 정확도는 별개입니다.** 전체 표 2,320개가 연결됐어도 모든 셀·단위·아이콘을 정확히 읽었다고 볼 수는 없습니다.

## 3. 청킹 규칙

청킹은 직접 작성한 Python 코드로 수행했습니다. LangChain TextSplitter를 사용한 방식은 아닙니다.

1. **공백·제목·표 헤더를 포함한 500자**를 기본 상한으로 잡았습니다. 500토큰이라는 뜻은 아닙니다.
2. 같은 매뉴얼·페이지에서 같은 제목·열에 속하고 가까운 본문을 먼저 묶습니다. 인접 문장들을 순서대로 500자 안에 담습니다.
3. 긴 문장은 문장 경계를 우선하고, 하나의 문장이 너무 길면 쉼표·세미콜론 등의 구절 경계, 그다음 단어 경계로 나눕니다.
4. 일반 분할은 마지막 완전한 문장이 100자 이하일 때 다음 청크에 반복합니다. 긴 문장을 쪼갠 경우에는 끝부분을 단어 경계에 맞춰 최대 100자 겹칩니다. 겹침 때문에 다음 문장을 불필요하게 자르게 되면 겹침을 생략합니다.
5. 나눈 조각을 마지막에 전부 하나로 합치지는 않습니다. 검색으로 선택한 청크와 연결된 부모 문맥을 답변할 때 함께 사용합니다.

| 유형 | 처리 방식 |
|---|---|
| 본문 | 같은 제목·열의 가까운 문단을 묶고 문장·구절 경계로 분할 |
| 그림 | 이미지 파일이 아니라 **description 텍스트**를 그림별로 청킹 |
| 표 | HTML을 `열 이름: 셀 값` 등의 검색 텍스트로 변환. 행 경계를 우선하고 긴 행은 셀 단위로 분할. 필요한 헤더·행 이름을 반복하며 앞 행을 겹치지는 않음 |

병합 셀 참조와 출처 ID·이미지 경로·좌표·문자 범위 또는 표 행·셀 참조를 남겼습니다. 헤더나 구조가 불확실하면 표시하고 원본 HTML은 유지했습니다.

최종 청크는 **본문 85,849 / 그림 설명 26,546 / 표 7,624 / 제목 6,919개**입니다. 원본 그림·표 하나가 여러 청크가 될 수 있습니다. 긴 표 문맥 26개는 500자 초과 예외로 보존했으며 최대 1,776자였습니다.

500자는 검색의 세밀함과 문맥 유지 사이에서 정한 초기 기준입니다. 다른 길이와 비교해 최적값임을 입증한 상태는 아닙니다.

## 4. 임베딩과 벡터 DB 저장

| 구성 | 설정·역할 |
|---|---|
| 임베딩 모델 | `qwen3-embedding:0.6b`, Q8_0, 1,024차원 |
| GPU 처리 | 배치 4, 동시 요청 1, 문맥 2,048토큰, `truncate=false` |
| 문서·질문 | 같은 임베딩 모델과 벡터 공간 사용. 질문에는 검색용 영어 지시문 추가 |
| SQLite | 생성한 임베딩을 저장하는 캐시. 중단 후 재개·재계산 방지용 |
| Qdrant | 로컬 디스크 모드. 의미 벡터·BM25 희소 벡터·청크 본문과 출처 저장 |

그림은 description, 표는 행·셀 텍스트를 임베딩했습니다. **CLIP·SigLIP 같은 이미지 임베딩이나 원본 이미지 픽셀 입력은 적용하지 않았습니다.** 임베딩 모델을 별도로 학습하거나 모델 가중치를 수정한 것도 아닙니다.

2026-10-26 전체 실행은 청킹·임베딩·적재·검증까지 약 **1시간 51분**이었습니다. 이후 LangChain·Qdrant 검색 전환과 부모 문맥·프롬프트 실험에서도 기존 문서 의미 벡터를 재사용했습니다.

현재 SQLite는 키워드 검색 엔진이 아닙니다. 초기에는 SQLite FTS와 코드상의 점수 결합을 시험했지만, 이후 **Qdrant 내부 의미·BM25 검색과 가중 RRF**로 전환했습니다. 현재 새 질문 벡터는 별도 JSON 캐시에 저장합니다.

## 5. 현재 검색·답변 흐름

```text
사용자 질문 + 대상 매뉴얼
 → Qwen3.5로 한국어 질문을 영어로 번역
 → Qwen 질문 임베딩 + BM25 질문 벡터
 → Qdrant에서 해당 매뉴얼만 검색
 → 의미·키워드 검색 순위를 가중 RRF로 결합해 Top-k 선택
 → 연결된 부모 문맥 추가·중복 제거·입력 길이 제한
 → 원래 한국어 질문과 근거를 Qwen3.5-4B에 전달
 → 한국어 답변과 근거 ID를 검증하고 원본 위치 연결
```

LangChain은 번역·검색·답변 도구를 연결하는 프레임워크입니다. 의미 검색은 Qdrant의 코사인 유사도를 사용하고, 키워드 검색과 순위 결합도 Qdrant에서 수행합니다.

- **키워드 0%:** 의미 검색만 사용합니다. 100%는 BM25만, 중간 값은 두 검색 순위의 결합 비중입니다. 답변 비율이나 LLM 학습 가중치가 아닙니다.
- **Top-1/5:** 최초 검색 청크 수입니다. Top-5도 답변은 하나를 만듭니다. 부모 연결 후에는 추가 근거가 들어가므로 최종 근거 수는 5개보다 많을 수 있습니다.
- **답변 모델:** `qwen3.5:4b` Q4_K_M, `think=false`, temperature 0, 문맥 8,192토큰, 출력 최대 1,024토큰입니다. 질문 임베딩 후 임베딩 모델을 내리고 답변 모델을 사용합니다.
- **출력:** `answer`, `source_ids`, `insufficient_evidence`를 받아 실제 청크·페이지·좌표에 연결합니다. 이미지 경로·좌표는 있으나 답변 LLM에 원본 이미지 바이트를 넣거나 화면에 표시하지는 않습니다.

## 6. 부모 문맥과 프롬프트 보완

**부모 문맥:** 같은 페이지의 소제목 아래 본문·표·그림, 도면 내부 레이블, 한 제목 아래 연속 번호가 있는 양쪽 열의 절차를 연결했습니다. 검색한 청크를 우선하고 부모별로 문맥을 추가하되 중복과 입력 예산을 검사하며 최대 32개 근거를 사용합니다. 연결이 불확실하면 같은 원본 영역 안에서만 확장합니다.

전체 126,938개 청크에 연결 지도를 작성했으며 기존 임베딩·DB는 유지했습니다. 일부 제목 접두어 보정도 답변 입력용 사본에만 적용했습니다. `ParentDocumentRetriever`의 작은 청크 검색 후 부모를 조회하는 원리를 적용한 **전용 확장기**이며 해당 클래스를 그대로 사용한 것은 아닙니다. 페이지를 넘는 절차 연결과 모든 연결의 의미 검수는 아직 하지 않았습니다.

**프롬프트 수정안:** 질문하지 않은 부연을 줄이고, 필수 조건·수치 범위·표의 행열 대응·대안과 순서를 보존하도록 지시를 바꿨습니다. 동일한 근거 내용·개수·순서와 같은 모델 설정으로 답변 60개를 다시 생성했습니다. 평균 답변 길이는 약 15% 줄었으나 전체 정답률은 개선되지 않았습니다.

현재 **부모 문맥은 기본 적용**, 일반 실행의 프롬프트는 **기존 `pm209-grounded-ko-v1` 유지**입니다. 새 `pm209-focused-ko-v2`는 `--answer-prompt focused`로 선택하는 실험안입니다.

## 7. 비교 결과와 해석

본문·표·그림 질문 각 10개, 총 30문항의 **최종 답변 정답률**입니다. 부분정답·미답변·형식 오류도 분모에 포함했습니다. 검색 성공률이나 전체 PM209의 정확도와는 다릅니다.

### 가중치·Top-k 비교: 부모 연결 전, LangChain + Qdrant

| 키워드 비중 | Top-1 정답률 | Top-5 정답률 |
|---|---:|---:|
| 0% | 50.0% | 66.7% |
| 25% | 43.3% | 60.0% |
| 50% | 46.7% | 60.0% |
| 75% | 46.7% | 60.0% |
| 100% | 33.3% | 53.3% |

이 비교에서는 답변 300개를 생성했습니다. 앞서 수행한 번역·외부 키워드 검색·본문 질문만의 실험은 별도 기록이며, 검색 구현이 달라 위 결과와 섞어 집계하지 않았습니다.

### 부모 문맥과 프롬프트 변경: 최초 검색 Top-5 고정

| 키워드 비중 | 부모 연결 전 | 부모 연결 + 기존 프롬프트 | 부모 연결 + 수정 프롬프트 |
|---|---:|---:|---:|
| 0% | 66.7% | **73.3%** | 70.0% |
| 50% | 60.0% | **66.7%** | 63.3% |

| 유형 | 부모 연결 + 기존 프롬프트: 0% / 50% | 수정 프롬프트: 0% / 50% |
|---|---:|---:|
| 본문 | 90.0% / 80.0% | 90.0% / 90.0% |
| 표 | 80.0% / 70.0% | 80.0% / 50.0% |
| 그림 | 50.0% / 50.0% | 40.0% / 50.0% |

- 부모 연결로 구성품 표·연결 포트·설치 후반 단계 등의 누락이 보완됐습니다. 표 정답률은 두 비중 모두 연결 전보다 20.0%p 올랐습니다.
- 부모 연결 후 **답변에 충분한 근거가 들어간 비율은 두 비중 모두 86.7%**였습니다. 그러나 LLM이 조건을 빠뜨리거나 불필요한 수치를 섞어 최종 정답률은 달랐습니다. 충분한 근거의 존재와 정확한 답변 생성을 따로 평가해야 합니다.
- 입력 전압 질문에서는 두 비중에 같은 18개 근거가 다른 순서로 들어갔습니다. 기존 프롬프트의 50% 답변은 전류까지 부연하다가 오류를 냈습니다. 순서의 영향이 의심되지만 순서만 분리한 실험으로 인과관계를 확정한 것은 아닙니다.
- 수정 프롬프트에서 전류 부연 오류는 줄었지만 삭제 방식 혼합, 재시작 권장 누락, 초기화를 데이터 복구처럼 설명하는 오류가 생겼습니다. 일반 실행의 기본 프롬프트를 교체하지 않은 이유입니다.
- 그림의 버튼 위치·아이콘·해제 방향이 설명 텍스트에 없으면 부모 문맥이나 프롬프트만으로 복원하기 어렵습니다.

**이번 표본의 최고는 부모 문맥 + 기존 프롬프트 + 키워드 0%였습니다.** 실행기의 키워드 기본값은 여전히 50%이며 최적값으로 확정한 값은 아닙니다. 같은 개발 문항을 Codex가 고정 기준으로 검수한 결과로, 새 질문에 대한 독립 평가·반복 생성의 변동성 측정은 남아 있습니다. 일부 QA의 원본 불일치에 대한 기존 보정 기준도 유지했습니다.

## 8. 완료·남은 작업 체크리스트
