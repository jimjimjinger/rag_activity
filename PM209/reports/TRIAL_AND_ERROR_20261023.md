# PM209 그림 설명·표 추출 시행착오

정리일: 2026-10-23. 실제 실행 기록, 코드, 샘플 검수, 최종 보존 검증을 기준으로 정리했습니다. 그림·표의 추출 완료와 내용의 의미 정확도는 구분합니다.

## 작업 목표와 현재 상태

PM209의 기존 페이지 JSONL을 사용했습니다. `image_filename`으로 페이지 JPG를 열고, 기존 영역의 `shape` 좌표로 메모리에서 잘라 모델에 전달했습니다. 페이지 전체를 다시 OCR하거나 영역을 다시 검출하는 작업은 하지 않았습니다. QA 질문·정답을 모델 입력으로 사용하지 않았습니다.

| 대상 | 처리 방식 | 최종 상태 |
|---|---|---|
| 그림 | Qwen3.5-4B로 잘라낸 그림을 해석하고 기존 객체에 `description` 추가 | 23,807개 생성·저장, 누락 0개 |
| 표 | PaddleOCR `TableRecognitionPipelineV2`로 OCR과 구조 인식을 결합하고 기존 Table 객체에 HTML `table_content` 추가 | 2,308 / 2,320개 저장, 12개 미완료 |
| 기존 데이터 | 본문·페이지·영역·ID·좌표·QA와 앞서 생성한 그림 설명 보존 | 10,018페이지·211,609영역·22,021 QA 보존 확인 |

청킹·임베딩·검색·답변 생성은 이 작업에 포함하지 않았습니다.

## 1. 그림 설명: 생성 길이와 오류 처리

### 문제 1 — 설명이 출력 토큰 한도에 도달해 전체 실행이 멈춤

첫 전체 실행은 3,493개를 저장한 뒤 그림 하나의 응답이 출력 한도에 도달하면서 중단됐습니다. 당시 문제는 응답 생성 길이와 처리 정책이었습니다. 이 기록만으로 VRAM 부족이나 과열이 원인이었다고 판단할 수는 없습니다.

복잡한 그림을 자세히 설명하도록 두면 출력이 길어지거나 반복될 수 있습니다. 응답이 잘려 JSON 형식까지 완성되지 않으면 그 설명을 정상 결과로 저장할 수 없습니다.

대응:

- 새 설명을 영어 2~4문장, 최대 100단어의 간결한 내용으로 요청했습니다.
- 재시도 시 두 문장, 최대 60단어·40단어로 요구를 줄였습니다.
- 그림별 최대 3회 시도 후 계속 실패하면 기록하고 다음 그림으로 넘어가도록 바꿨습니다. 전체 순회 후 미완료 그림을 다시 확인합니다.
- 문장 수는 프롬프트 지침이고, 단어 수·JSON 형식·응답 잘림은 코드로 검사합니다. 짧게 쓰라는 지시만으로 잘림이 없어지는 것은 아닙니다.
- 출력 한도 768토큰과 문맥 4,096토큰은 유지했습니다. 그림 하나씩 처리하고 긴 변 최대 1,536픽셀, 추론 모드 끄기를 적용했습니다.

결과: 기존 저장분부터 재개할 수 있게 됐습니다. 초반 3,493개는 이전 프롬프트 결과를 유지했으므로, 전체 설명이 모두 새 길이 규칙으로 재생성된 것은 아닙니다.

### 문제 2 — 생성 도중 토큰 반복 오류가 별도 예외로 발생

22,798개까지 저장한 시점에 Ollama가 `token repeat limit reached`를 반환하면서 다시 중단됐습니다. 이는 같은 토큰·패턴의 반복을 모델 서버가 감지한 오류입니다. 앞선 정상 응답의 길이·JSON 검사와는 다른 예외 경로에서 발생해 별도 처리가 필요했습니다.

대응:

- 해당 서버 예외를 그림별 재시도 대상에 추가했습니다.
- 정상 응답 객체가 없는 경우에도 오류 메시지를 안전하게 기록하도록 했습니다.
- 저장한 22,798개를 재사용하고 남은 1,009개만 생성했습니다.
- 이 예외 처리에 대한 회귀 검사를 추가했습니다.

결과: 재개 중 반복 오류 1회가 재시도로 해결됐고, 2026-10-22 15:06 KST 전체 23,807개 생성·저장을 완료했습니다.

### 문제 3 — 장시간 처리 중 중단되면 재작업 비용이 큼

대량 처리에서는 그림 하나의 실패가 전체 결과를 무효화하거나, 저장하지 않은 결과를 완료로 보고하는 문제가 생길 수 있습니다.

대응:

- 100개 단위 체크포인트와 저장분 재사용을 적용했습니다.
- `completed`와 최종 JSONL에 반영된 `saved`를 구분했습니다.
- 실패 ID·원인, 지연 처리 대상과 진행 상태를 기록했습니다.
- 동시에 실행기 하나만 동작하도록 했습니다.
- 정상 중단·재개 경로를 마련하고 원본과 보강본을 대조했습니다.

결과: 중단 후 남은 그림부터 이어서 처리할 수 있었고, 최종 누락 0개와 기존 데이터 보존을 확인했습니다. 이 검증이 설명 내용 전체의 정확도를 인증하는 것은 아닙니다.

## 2. 표: 생성 모델 방식에서 OCR·구조 인식으로 전환

### 문제 4 — Qwen으로 표 전체를 생성할 때 형식·반복 문제가 많았음

그림 설명에 쓰던 Qwen으로 표를 HTML 또는 Markdown으로 생성하는 실험을 진행했습니다. 표는 문장 요약과 달리 셀 값, 행·열, 병합 관계를 길게 일관되게 출력해야 했습니다. 실험에서는 구조 오류·반복 출력과 과도한 형식 검증으로 실패가 많았습니다. Markdown으로 바꾸는 것만으로 문제가 해결되지 않았습니다.

대응: 사용자 요청으로 해당 표 실험을 중단하고 표 전용 코드·결과·로그를 정리했습니다. 이미 완료한 그림 description은 유지했습니다. 이어서 전용 `TableRecognitionPipelineV2`로 방법을 바꿨습니다.

이 결정은 이번 장비·데이터·실험에서의 선택입니다. HTML 형식 자체가 불가능하다거나 VLM이 모든 표에 부적합하다는 결론은 아닙니다. 폐기한 실험의 세부 로그·실패 건수는 현재 보존돼 있지 않아 정확한 실패율을 제시하지 않습니다.

### 문제 5 — Windows·RTX 50 계열 설치와 한글 경로 문제

표 전용 실행 환경을 별도로 구성했습니다. Windows 11·RTX 5060 Laptop·VRAM 8GB에 맞는 공식 PaddlePaddle GPU 빌드를 사용했고, 모델 초기화 중에는 C++ 로더가 한글 작업 폴더 아래의 모델 파일을 열지 못하는 문제가 실제로 발생했습니다.

대응:

- `.runtime/venv-paddle-tables` 전용 환경으로 기존 환경을 보존했습니다.
- Windows RTX 50용 CUDA 12.9·cuDNN 9.9 GPU 빌드, PaddleOCR 3.3.2·PaddleX 3.3.11을 사용했습니다.
- 모델 캐시를 한글 경로 밖인 `%LOCALAPPDATA%/PM209-PaddleTables/paddlex`로 옮겼습니다.
- 표 하나씩 처리하고 OCR 배치 1, Paddle 메모리 할당 한도 6,144MiB를 설정했습니다. 이 한도와 장치 전체 VRAM 실측은 별개입니다.
- 이미 Table 위치를 알고 있으므로 레이아웃 분석·방향 분류·왜곡 보정을 껐습니다.

결과: GPU 모델 로딩과 표 예측이 정상 동작했습니다. `ccache` 미설치 경고는 실행 중단 원인이 아니었습니다.

### 문제 6 — HTML 출력 성공과 표 내용 정확도가 달랐음

일반 표·병합 표·내용이 많은 표를 하나씩 먼저 시험했습니다. 세 개 모두 HTML을 반환했지만 내용 오류가 있었습니다.

| 표본 | 확인 결과 | 남은 오류 |
|---|---|---|
| 일반 표 | 4행×4열과 숫자·행열 대응·마지막 행 보존. 정규화 후 11/16셀 일치 | `27°C`가 `27°℃` 등으로 바뀜. 습도 `-` 누락 |
| 병합 표 | 5행×5열, 확인한 병합 3개와 전력 값 보존. 20/21셀 일치 | `Inactive`가 소문자 l로 시작하는 `lnactive`로 인식됨 |
| 내용이 많은 표 | 11행×2열, 문제·해결 대응과 끝부분 보존 | 전원·팬·운전 모드 아이콘 누락·오인식. 본문이 남아 있어도 조건의 의미가 일부 손실됨 |

대응: 문자·숫자·단위, 행열·병합, 마지막 행·본문의 누락을 따로 검수했습니다. 아이콘·단위·낮은 OCR 신뢰도 등을 검수 우선 대상으로 표시했습니다. 모든 오인식을 자동 수정한 것은 아닙니다.

위 셀 일치 수치는 두 표본의 결과이며 전체 표의 정확도로 일반화할 수 없습니다. 내용이 많은 표에는 전체 정확도 백분율을 부여하지 않았습니다.

## 3. 전체 표 처리: 모델 오류와 검사 코드 오류를 분리

### 문제 7 — 첫 순회에서 232개가 동일한 HTML 오류로 제외됨

2,320개 전체 순회에서 2,088개를 저장하고 232개가 `Unbalanced table HTML`로 제외됐습니다. 실패 원시 결과를 확인하니 서로 다른 원인이 같은 오류 이름에 묶여 있었습니다.

- HTML에서 허용되는 `tbody` 등의 생략까지 엄격한 태그 스택 검사가 오류로 처리했습니다.
- 실제로 `thead`·`tbody`를 잘못 닫은 결과도 있었습니다.
- OCR 본문의 `<`, 코드 문자열 등이 HTML 태그처럼 해석돼 셀 경계가 깨지는 경우가 있었습니다.
- 실제 행·셀 마감 누락, 반복된 빈 행, 잘못된 병합·내용 누락도 있었습니다.

따라서 “232개 모두 표를 읽지 못했다” 또는 “모두 태그만 고치면 된다”는 설명은 부정확했습니다.

### 대응 1 — 재인식 없이 보정할 수 있는 범위를 제한

저장된 원시 결과를 유지하고 별도 폴더에서 행 그룹 태그를 정리하고 셀 내부 특수문자를 이스케이프했습니다. 셀의 텍스트·순서·속성·병합 위치가 보정 전후 같은지 비교했습니다. 빠진 셀이나 숫자를 추측해서 채우지 않았습니다.

처음 구분 태그를 제외한 임시 검사에서는 223개가 통과했지만, 이것은 복구 완료 수가 아니었습니다. 논리적인 셀 위치까지 확인하니 반복 빈 행·병합 문제 등이 추가로 드러나 **208개만 자동 복구**, **24개를 재인식 대상**으로 정했습니다.

검사 규칙도 보완했습니다. `rowspan` 때문에 위의 셀이 여러 행을 덮고 있다면 내용이 없는 행이 정상적으로 존재할 수 있습니다. 이런 행은 단순히 빈 행이라는 이유로 오류 처리하거나 삭제하지 않았습니다.

### 대응 2 — 구조 문제가 남은 24개만 GPU 재인식

같은 `TableRecognitionPipelineV2` 안에서 다음 설정을 필요한 표에만 단계적으로 비교했습니다.

| 변경 | 비교 목적 |
|---|---|
| RT-DETR가 검출한 셀 좌표를 HTML 구조로 변환 | 반복되는 구조 출력의 영향을 줄일 수 있는지 확인 |
| 입력 1.5배 확대 | 작은 글자·셀 검출 차이 확인 |
| 셀별 OCR 결과와 전체 OCR 결과의 결합 방식 변경 | 문장 누락·셀 연결 오류 개선 여부 확인 |
| 잘라낸 표에 흰 여백 24px 추가 | 표 가장자리 조건이 인식에 미치는 영향 확인 |
| SLANeXt 자체 셀 좌표와 OCR 결합 | 검출 셀과 구조 모델의 대응 차이를 비교 |

모든 설정이 항상 개선 효과를 보인 것은 아닙니다. 형식 검사를 통과한 후보도 원본과 비교하면 마지막 행이 빠지거나 서로 다른 열의 내용이 붙는 경우가 있었습니다. 후보는 모두 보관하고, 모델이 반환한 원시 HTML과 보정 HTML을 구분했습니다.

결과: 24개 중 **12개 채택**, **12개 미완료**입니다. 일부 후보는 처음 실패 때보다 악화돼 채택하지 않았습니다. 24개에 대한 비교 요청은 총 70회였으며 같은 전체 2,320개를 반복 실행한 것은 아닙니다.

### 아직 해결하지 않은 12개

대표적인 문제는 다음과 같습니다.

- 프린터 명령 설명처럼 긴 문장과 작은 내부 표가 섞인 영역: Range·Notes·Default·Reference 누락, 셀 연결 오류.
- 에어컨 오류 코드 표: 마지막 `E31` 행 누락, Operation/Timer/Ready 열 합침, 상태 아이콘 손실.
- 세탁기 오류 표: E4 설명 위치 오류와 마지막 E9 행 누락.
- 리모컨 버튼 설명: 뒤쪽 PIP·SWAP 설명 누락.
- 사양·안내 표: 크기·무게·마지막 제품명 등 뒷부분 누락, 2열을 3열로 잘못 나눔.

이 표들은 성공 수에 넣지 않았고, 실패 원인과 후보를 남겼습니다. 채택한 12개도 일부 단위·아이콘·문자 오류가 남아 완전히 정확한 표로 인증한 것은 아닙니다.

## 4. 결과 관리에서 배운 점

| 문제 | 대응 |
|---|---|
| 표 하나의 실패가 전체 실행을 중단시킬 수 있음 | 표별 실패 기록 후 다음 표 처리, 정상 결과 즉시 저장 |
| 생성했지만 최종 JSONL에 저장하지 않은 수를 완료로 오해할 수 있음 | 완료·저장·저장 대기 수를 구분하고 체크포인트·재개 기록 유지 |
| 재처리로 기존 성공 결과나 그림 설명이 바뀔 위험 | 첫 결과와 보완본 분리, 기존 성공 2,088개·원본 6개 파일·전체 페이지 필드 보존 대조 |
| 검수 PNG·단계별 JSONL을 모두 전송하면 용량이 큼 | 전송본은 이미지와 중복 단계 파일을 제외하고 최신 JSONL·코드·MD로 구성. 로컬 기존 결과는 유지 |
| 원본 JSONL도 약 258MB라 결과가 갑자기 커진 것으로 오해 | train 기준 그림 추가 후 약 263MB, 표 추가 후 약 264MB. 대부분은 원래 본문·좌표·QA의 용량임을 구분 |

최신 JSONL 하나에 앞 단계의 데이터와 새 필드가 같이 남아 있으므로, 중복 단계 파일은 추가 필드를 제거해 복원할 수 있습니다. 전송본의 복원 도구는 원본·그림 보강본·첫 표 보강본의 9개 JSONL을 원래 SHA256과 대조했습니다. Windows 줄바꿈 차이도 보존했습니다.

검수 PNG는 로컬에서 표 2,320개와 보완본의 중복 220개를 저장했습니다. 전송 ZIP에서는 제외했지만 로컬에서 삭제한 것은 아닙니다. 그림 설명 대상 23,807개 전체를 별도 그림 파일로 저장한 것은 아닙니다.

## 최종 수치의 해석

```text
그림: 23,807개 생성·저장, 누락 0개

표: 첫 성공 2,088개
    + 형식 보완 208개
    + 재인식 채택 12개
    = 2,308개 저장 / 2,320개 대상
      미완료 12개
```

**99.48%는 표 결과의 저장·추출 커버리지이지 인식 정확도가 아닙니다.** 전체 그림 설명과 표 내용의 의미 정확도 평가, 실제 질의의 검색·답변 성능 평가는 별도로 남아 있습니다.
