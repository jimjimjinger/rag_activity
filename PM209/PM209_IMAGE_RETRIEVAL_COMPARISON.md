# PM209 문서 보강과 RAG 설계

갱신일: 2026-10-26

기존 파싱 결과를 재사용하고 그림 설명과 표 내용을 추가했다. 2026-10-26에는 아래 규칙을 바탕으로 청킹·임베딩·Qdrant 저장·검색을 구현하여 3개 매뉴얼 48페이지에서 실행했다. 이후 전체 209개 매뉴얼의 126,938개 벡터 저장·검증을 완료했다([전체 결과](reports/RAG_FULL_RUN_20261026.md)). 답변 생성은 수행하지 않았다. [실행 방법](RAG_PIPELINE.md), [샘플 평가와 남은 문제](reports/RAG_SAMPLE_20261026.md)를 별도로 기록했다.

## 현재 결정

| 항목 | 결정 |
|---|---|
| 본문·제목 | 제공된 JSONL의 단어와 좌표 재사용 |
| 그림 대상 | Product Image, illustration, graphic |
| 그림 입력 | 페이지 JPG에서 기존 shape로 자른 이미지와 고정 지시문 |
| 설명 모델 | Qwen3.5-4B, Ollama 태그 qwen3.5:4b |
| 모델 연결 | LangChain ChatOllama |
| 생성 언어 | 영어, 읽을 수 있는 원문 글자·숫자·단위도 포함 |
| 저장 | 기존 그림 객체에 description 문자열 하나 추가 |
| 표 | PaddleOCR HTML 2,308개 + 이미지 기반 수기 요약 HTML 12개; 수기 보강은 재검수 필요 |
| 청킹 초안 | 페이지를 상위 문맥으로 보존하고 본문 묶음·그림 설명·표/표 행 묶음을 검색 단위로 사용 |
| 검색 임베딩 | Qwen3-Embedding-0.6B, Ollama Q8_0, 1,024차원, 샘플 GPU 실행 |
| 벡터 DB | Qdrant 로컬 디스크 모드, 전체 126,938개 저장·검증 완료 |
| 답변 | 후속 단계에서 Qwen3.5-4B로 한국어 생성 |
| 검색 범위 | 사용자가 선택한 매뉴얼 전체 |

CLIP으로 본문과 그림을 매칭하는 방식도 검토했지만, 현재 구현 범위에는 포함하지 않는다. 그림 설명을 검색 단서로 만드는 방식을 선택한 것이며, CLIP보다 정확하다고 비교 실험으로 입증한 결정은 아니다.

## 원본과 보강본

PM209의 제공 좌표를 활용하므로 그림 영역을 새로 검출하지 않는다. `image_filename`으로 페이지를 열고, 해당 그림의 `shape`에서 x·y·width·height를 읽어 영역을 자른다. 페이지 ID로 이미지 파일명을 추정하지 않는다.

```text
페이지 레코드
├── id                         유지
├── image_filename             유지
├── bounding_boxes[]
│   ├── 본문·제목 영역         기존 필드 유지
│   ├── 표 영역               기존 필드 + table_content
│   └── 그림 영역
│       ├── id                 유지
│       ├── structure          유지
│       ├── shape              유지
│       └── description        추가하는 유일한 필드
└── qa_data                    유지, 모델 입력에는 제외
```

`visible_text`, `uncertainties`, `vlm_info` 등 별도 생성 필드는 추가하지 않는다. 그림의 관찰 가능한 부품·조작·화살표·위치 관계와 읽을 수 있는 표기를 description에 담는다. 보이지 않는 기능·조작 시간·판독 불가능한 숫자를 추측해 채우지 않도록 지시한다.

본문·정답·정답 근거 영역을 VLM에 넣지 않는다. 원본 JSONL과 JPG는 수정하지 않고 `datasets/PM209/data/vlm/{split}.jsonl`에 보강본을 저장한다. 일부 그림만 처리해도 해당 split의 모든 페이지와 기존 정보를 보존한다.

그림 보강 이후 `Table`에는 별도 PaddleOCR 파이프라인으로 HTML `table_content`를 추가했다. 현재 별도 수기 보강본에는 2,320개 Table 모두 내용이 있지만, 그중 12개는 원본 셀 구조를 그대로 복원한 결과가 아니라 이미지 기반 요약 전사다. 청킹에서 출처와 검수 상태를 유지한다. 세부 이력은 [작업 안내](README.md)에 있다.

## 저장과 재개 구현

`src/describe_images.py`는 최종 저장 형식에 맞게 수정했다. 같은 출력의 기존 description을 재사용하고, 추가 처리 개수는 새 설명만 센다. 기존 보강본은 원본과 대조해 description 외의 변경을 거부한다.

페이지를 순서대로 읽고 임시 JSONL에 기록해 전체 데이터를 메모리에 올리지 않는다. 생성 한도에 도달하거나 생성 오류·Ctrl+C가 발생해도 나머지 페이지를 복사하여 보강본을 완성한 뒤 교체한다. 원본 대조 실패 시에는 기존 정상 보강본을 유지한다.

프로세스 강제 종료·전원 차단 시 마지막 정상 저장 이후의 생성 결과는 재처리할 수 있다. 남은 `.jsonl.tmp`는 자동 덮어쓰기하지 않는다. 설정을 바꿀 때는 별도 출력 경로를 사용한다. 현재 코드가 결과 보고서를 자동 생성하지는 않으므로 모델·설정·처리 범위는 실행 후 작업 기록에 남긴다.

## 데이터와 메타데이터

데이터는 `datasets/PM209`에 있다. 209개 매뉴얼·페이지 JPG 10,018장·QA 22,021개를 제공한다. 원본 PDF는 배포 ZIP에 없다.

메타데이터는 공식 ZIP과 별도로 [공식 저장소의 meta_data](https://github.com/AIM3-RUC/MPMQA/tree/master/meta_data)에서 제공한다. `meta_data/name2meta.json`은 매뉴얼 ID를 브랜드·제품 종류에 연결한다. 설명 생성에는 필수가 아니지만 제품·매뉴얼 선택과 검색 필터링에 활용한다. 두 brand_and_product 파일은 브랜드·제품별 개수 집계다.

## GPU에서 확인할 순서

1. [실행 안내](README.md)에 따라 NVIDIA GPU·실제 VRAM·Ollama 버전과 비전 모델을 확인한다.
2. `--preview --types illustration graphic --limit 3`으로 원본 좌표의 그림을 확인한다.
3. 같은 범위의 그림 3개에 설명을 생성하고 실제 그림과 대조한다.
4. 숫자·단위·버튼명, 화살표·조작 순서, 누락·추측을 확인한다. 처리 시간과 메모리도 기록한다.
5. 소량 결과를 보고 다음 처리 범위를 정한다. 전체 데이터를 자동 실행하지 않는다.

기본 설정은 그림 1개씩, 긴 변 최대 1,536픽셀, 컨텍스트 4,096토큰, 출력 최대 768토큰, temperature 0, 추론 모드 끄기다. 모델 GPU 자동 적재를 요청하고 첫 생성 후 Ollama의 적재 상태를 확인한다. 부분 적재와 전체 GPU 실행은 구분한다. 출력 잘림·잘못된 형식·GPU 적재 확인 실패는 성공 설명으로 저장하지 않는다.

2026-10-22부터 새 설명은 영어 2~4문장, 최대 100단어를 목표로 핵심만 요청한다. 설명 길이·형식 오류는 그림별 최대 세 번 시도하며, 계속 실패하면 ID를 기록하고 다른 그림을 계속 처리한다. 전체 처리 후 미완료 항목을 한 차례 더 시도하며, 끝까지 남은 항목은 `needs_review`로 표시한다. 먼저 저장한 3,493개는 기존 프롬프트 결과를 재사용한다.

Ollama의 `token repeat limit reached`는 생성 도중 발생하는 예외이므로 일반 응답 검증과 별도로 포착하여 같은 재시도·보류 경로로 처리한다. 저장된 설명은 반복 생성하지 않는다.

기존 `.runtime`과 `.venv`를 재사용해 실제 GPU 표본 23개를 생성했다. 표본 실행 당시 train 보강본은 7,004페이지·QA 15,839개를 보존하며 그림 23개에 description을 추가했다. 종류·크기별 외삽은 약 14시간이며 작업 여유를 두면 15~20시간으로 잡는다. 일부 작은 글자·기호의 추측 오류가 있어 설명 정확도는 별도 점검이 필요하다. 2026-10-21 19:15 KST 전체 23,807개 처리를 시작했으며, 100개마다 저장한다. 현재 진행 상태는 `.runtime/pm209-full/status.json`에서 확인한다. [GPU 표본 실측](reports/GPU_SAMPLE_20261021.md)

## 후속 RAG 단계

```text
본문 단어와 영역 좌표 재사용 + 그림 description + 표 table_content
  → 본문 묶음·그림 설명·표 행 묶음 구성, 페이지·원본 영역 연결
  → Qwen3-Embedding-0.6B로 벡터화
  → Qdrant에 출처·매뉴얼 ID와 함께 저장
  → 선택한 매뉴얼 전체에서 한국어 질문 검색
  → Qwen3.5-4B가 검색된 텍스트로 한국어 답변 생성
  → 답변에 사용한 근거 ID에 연결된 그림만 표시
```

그림 설명은 특정 문단에 강제로 붙이지 않고 독립 검색 자료로 사용할 계획이다. 질문마다 그림을 다시 해석하는 구성은 현재 포함하지 않는다. description에 빠진 정보는 텍스트 답변 모델이 원본 이미지를 보고 보충할 수 없다.

청킹은 아래 초안을 소량 데이터에서 시험했으며 Qdrant는 로컬 저장 모드를 사용한다. 최종 검색 개수, 답변의 근거 ID 반환 형식과 UI는 후속 단계에서 구체화한다. 같은 Qwen 계열 사용이 정확도 향상을 보장하지는 않는다.

## 청킹 규칙 초안 v0.2 — 원 논문 참고

작성일: 2026-10-26. **현재 청크 길이는 공백 포함 500자, 겹침은 최대 100자다.** 사용자가 선택한 글자 수 기준이며, 앞서 제안한 토큰 기준과 구분한다. 아래 묶음 규칙·중복 판정 기준은 우리 프로젝트의 설계이며 원 논문에서 검증한 설정이 아니다. 48페이지 샘플 구현·검색 검증은 수행했으며 전체 데이터의 적합성은 아직 확정하지 않았다.

### 적용 체크리스트 — 항목별 두 가지

아래 체크박스는 전체 적용 시 확인할 기준이다. 일부를 샘플에서 구현·검증했지만 전체 데이터 검증 완료를 뜻하지 않으므로 일괄 체크하지 않는다. 제목/열은 좌표 휴리스틱, 구조가 깨진 표는 셀 순서 보존 예외를 사용했다. 샘플의 정확한 범위와 예외는 [실행 안내](RAG_PIPELINE.md)에 있다.

**1. 검색 목적**

- [ ] 기능 설명·사용 절차·오류 해결·제품 사양 질문에 답할 수 있는 내용을 검색 자료로 구성한다.
- [ ] 사용자가 선택한 매뉴얼 하나의 전체 페이지를 검색 범위로 한다.

**2. 본문을 묶는 기준**

- [ ] 같은 페이지·같은 제목·같은 열에서 의미가 이어지는 문단과 단계를 묶는다. 다른 기능이나 제목으로 넘어가면 분리한다.
- [ ] 청크만 읽어도 대상을 알 수 있도록 확인된 제목·단계 번호·필요한 조건을 함께 둔다. 문맥이 필요한 경우 원본의 관련 내용을 연결하며 내용을 추측해서 보충하지 않는다.

**3. 그림·표 처리**

- [ ] 그림 설명은 그림별로 독립 구성하고 원본 이미지·좌표를 연결한다. 500자를 넘으면 본문과 같은 문장 분할 규칙을 적용한다.
- [ ] 표는 열 제목·행 이름·값·단위를 함께 보존한다. 500자 안이면 전체를 유지하고, 길면 행 묶음으로 나눠 필요한 헤더·단위를 반복한다. 단일 행도 길면 셀 내부 설명을 나눈다.

**4. 청크 길이와 겹침**

- [ ] 공백·제목·반복 헤더·겹친 내용을 포함한 검색용 텍스트를 500자 이내로 만든다. 문장·단계·표 행 경계를 우선하며, 문장 하나가 길면 구절·단어 경계에서 나눈다.
- [ ] 같은 내용이 이어질 때만 이전 청크의 마지막 완전한 문장을 최대 100자까지 반복한다. 마지막 문장이 100자보다 길면 일반 겹침을 생략하고, 긴 문장 자체를 분할한 경우에는 끝 구절을 최대 100자 반복한다. 다른 제목·기능·페이지로 넘어가면 겹치지 않으며, 표는 문장 겹침 대신 헤더를 반복한다.

**5. 출처와 데이터 구분**

- [ ] 매뉴얼·페이지·원본 영역 ID·좌표와 분할 위치를 기록해 출처를 찾을 수 있게 한다. 생성 설명·Paddle 표·수기 요약의 출처 및 검수 상태도 유지한다.
- [ ] QA 질문·정답·정답 근거 표시는 청크에 넣지 않고 평가에만 사용한다.

**6. 결과 확인**

- [ ] 대표 샘플의 원본과 청크를 비교해 누락·잘못된 묶음·의도하지 않은 중복·500자 초과를 확인한다.
- [ ] 실제 질문으로 필요한 본문·그림·표가 검색되는지 확인한다. train·val에서 규칙을 조정하고 test는 최종 평가에 사용한다.

### 1. 논문에서 확인한 내용

원 논문은 **MPMQA: Multimodal Question Answering on Product Manuals**, Zhang 외, AAAI 2023이다.

| 논문 근거 | 확인한 방식 |
| --- | --- |
| §3.1, §4.2–4.3 | 매뉴얼에서 페이지를 검색하고, 답변 문장과 관련 의미 영역을 선택한다. |
| §3.2, §4.1 | 본문·제목·그림·표 등의 영역을 구분하며, 페이지 입력에 영역 유형·단어·위치·시각 정보를 반영한다. |
| §3.2 | 연속 5페이지 묶음은 QA 작성자에게 제공한 주석 작업 단위다. 검색 청크 크기를 뜻하지 않는다. |
| §4.2 | 페이지 단일 벡터 유사도 대신 질문과 페이지의 토큰 간 상호작용을 사용한다. 우리 임베딩 검색과 구조가 다르다. |
| 부록 B–C | 영역 겹침을 허용한다. 여러 페이지를 근거로 하는 질문도 있어, 페이지 간 근거 연결을 고려해야 한다. |

따라서 논문의 고정 길이 RAG 청킹 규칙을 그대로 가져올 수는 없다. 참고할 원칙은 **페이지 문맥과 영역별 출처를 함께 보존하는 것**이다. [원 논문 본문·부록](https://arxiv.org/html/2304.09660v1)

공식 코드도 확인했다. `MQADataset.__getitem__`은 페이지 영역을 순회하며 유형 토큰과 OCR 단어를 연결한다. QA 입력은 `max_page_len`으로 잘라 반환하며, `parser.py`의 기본값은 1,024다. 이 값은 설정으로 덮어쓸 수 있는 모델 입력 제한이다. 1,024토큰 청크를 여러 개 만들어 벡터 DB에 넣는 규칙으로 해석하지 않는다. 검색용 `MQAContrastDataset`은 매뉴얼별 페이지 목록을 구성한다.

- 확인한 저장소 커밋: `5226a9aa849fd3b8f35620e7b7d7d10c09d754a2`
- [QA 페이지 입력 구성 코드](https://github.com/AIM3-RUC/MPMQA/blob/5226a9aa849fd3b8f35620e7b7d7d10c09d754a2/dataset/mqa_dataset.py#L133)
- [입력 길이 기본 설정](https://github.com/AIM3-RUC/MPMQA/blob/5226a9aa849fd3b8f35620e7b7d7d10c09d754a2/parser.py)
- [매뉴얼별 페이지 검색 데이터 구성](https://github.com/AIM3-RUC/MPMQA/blob/5226a9aa849fd3b8f35620e7b7d7d10c09d754a2/dataset/mqa_page_contrast.py#L37)

### 2. 로컬 데이터가 요구하는 보완

2026-10-26 `data/paddle_tables_manual_20261026/train.jsonl`의 `Text` 영역 105,012개를 읽고 각 `ocr_info` 항목 수를 집계했다. 중앙값 9개, 90백분위 36개, 95백분위 52개, 99백분위 97개, 최대 852개다. **이는 추출 단어 항목 수이며 임베딩 토큰 수가 아니다.** QA 내용은 이 집계나 규칙 결정에 사용하지 않았다.

영역마다 단독 청크를 만들면 짧은 항목이 많아 제목이나 앞뒤 문맥이 빠질 수 있다. 반대로 페이지 전체를 한 벡터로 만들면 긴 페이지 안의 개별 오류 코드·버튼·표 행을 찾는 성능을 확인해야 한다. 그래서 기본안은 **관련 본문 영역을 제한적으로 묶고, 그림과 표는 별도 검색 단위로 만드는 것**으로 잡는다. 페이지 단위 검색은 비교 실험의 기준으로 남긴다.

### 3. 공통 구조와 경계

```text
매뉴얼
  └─ 페이지: 원문 전체와 영역별 출처를 보관하는 상위 문맥
       ├─ 본문 청크: 같은 제목·같은 열의 인접 문단/절차
       ├─ 그림 청크: description + 확인 가능한 제목
       └─ 표 청크: 표 전체 또는 제목·열 이름을 포함한 행 묶음
```

- 청크는 하나의 매뉴얼·하나의 페이지 안에서 만든다. 페이지를 넘는 절차는 별도 청크와 페이지 연결로 처리한다. 서로 다른 매뉴얼을 합치지 않는다.
- 원본 영역 ID와 좌표를 유지한다. 여러 영역을 묶거나 하나를 나눠도 어느 부분에서 왔는지 추적한다.
- `bounding_boxes` 배열 순서나 ID 숫자를 읽기 순서라고 단정하지 않는다. 열 배치와 위아래 위치를 확인하고, 여러 열을 가로지르는 제목·표도 구분한다. 판단하기 어려운 배치는 영역을 억지로 합치지 않는다.
- 원본 단어 순서를 출발점으로 사용하고 대표 페이지에서 줄 순서를 확인한다. 줄바꿈 하이픈·소수점·오류 코드·단위를 무조건 삭제하거나 나누지 않는다.
- 데이터 원본의 `qa_data`는 보존하되, 청크 본문·제목·메타데이터에는 질문·정답·`answer.relevant`를 넣지 않는다. 이 정보는 평가 단계에서만 읽는다.

### 4. 자료 종류별 규칙

| 종류 | 기본 단위 | 묶기·분할 규칙 |
| --- | --- | --- |
| `Text` | 같은 제목 아래의 인접 문단 | 같은 열·같은 내용 흐름일 때 묶는다. 다른 제목, 별개 경고문, 다른 표·그림 설명으로 넘어가면 끝낸다. |
| `Title` | 연결할 본문·그림·표의 문맥 | 같은 열에서 해당 제목 아래에 있는 내용에 붙인다. 페이지 전체 제목과 소제목을 구분한다. 관계가 불확실하면 추정해서 붙이지 않는다. |
| `Product Image`, `illustration`, `graphic` | 그림 하나의 `description` | 그림별로 독립 검색한다. 가까운 본문이라는 이유만으로 강제로 합치지 않는다. 긴 설명만 문장 단위로 나누고 같은 그림 ID를 유지한다. |
| `Table` | 작은 표 전체 / 긴 표의 행 묶음 | 열 제목·행 이름·값·단위·필요한 각주를 함께 넣는다. 병합 셀과 헤더 관계를 해석한 후 텍스트로 만든다. |

**본문과 절차**

1. 제목과 관련 문단을 확인한 후 짧은 문단들을 읽기 순서대로 묶는다. 길이를 채우려고 다른 기능의 문단을 붙이지 않는다.
2. 번호 목록은 단계의 경계 정보로 사용한다. 모든 숫자를 청크 시작으로 취급하지 않는다. 오류 코드, 제품명, 치수, 그림 안의 번호도 보존한다.
3. 한 절차가 길면 단계 묶음으로 나누고, 각 묶음에 절차 제목과 단계 번호를 반복한다. 위험 경고·전제 조건은 관련 단계를 해석하는 데 필요하면 문맥으로 연결한다.
4. 연결할 내용이 없는 짧은 문단은 짧게 남긴다. 짧다는 이유로 누락시키지 않는다. 제목만 남는 경우에도 내용이 있는 제목은 독립 청크로 보존하고 유형을 기록한다.

**표**

1. HTML은 원본 결과로 보관한다. 검색용 텍스트는 HTML 파서로 행·열·`rowspan`·`colspan`을 읽어 별도로 만든다. 태그를 정규식으로 지우는 방식만으로 셀을 연결하지 않는다.
2. 다단 헤더는 상위 제목과 하위 열 이름을 함께 표시한다. 예를 들어 `전원 > 전압: 230 V`처럼 관계가 드러나도록 만든다. 이 표기는 설명용 예시이며 PM209에서 추출한 값은 아니다.
3. 빈 셀과 병합 셀을 구별한다. 병합 때문에 공유되는 이름은 각 해당 행의 검색용 문맥에 반복할 수 있지만, 값이 없는 셀에 앞 행 값을 임의로 복사하지 않는다.
4. 작은 표는 통째로 둔다. 긴 표는 연속된 행을 묶고, 각 청크에 표 제목·열 이름·관련 단위를 반복한다. 행에 연결된 각주를 포함하고, 각주 연결이 불명확하면 표 수준 문맥으로 보관한다.
5. 가능하면 세로 병합이 이어지는 행 묶음을 함께 둔다. 불가피하게 분할하면 공유된 행 이름을 명시한다. 한 행 자체가 매우 길면 행 이름·열 이름을 유지한 채 셀 내부 문장을 분할한다. 숫자 목록은 항목 경계에서 나눈다.
6. HTML이 불완전하거나 헤더·셀 관계를 확정할 수 없으면 해당 사실을 기록한다. 보기 좋은 표로 추정 복원하지 않는다.
7. 수기 보강 12개는 `manual_condensed_review_required`를 청크 메타데이터에 이어받는다. 2열 요약을 원래 표의 셀·병합 구조로 간주하지 않는다. 현재 저장된 내용을 사용하며 추가 수정은 이 청킹 설계 범위에 포함하지 않는다.

**표와 겹치는 본문 처리**

표 영역 안에 `Text` 영역이 함께 존재하므로 동일 문장이 두 종류의 청크에 들어갈 수 있다. 우선 텍스트 영역의 면적 중 표와 겹치는 비율이 90% 이상이면 중복 후보로 삼는다. 이 수치는 초기 제안이다.

좌표가 겹친다는 이유만으로 본문을 제거하지 않는다. 정규화한 문장이 표 검색용 텍스트에도 보존되는지 확인한 경우에만 중복 검색을 줄이고, 그 본문 영역 ID를 대응하는 표 청크에 연결한다. 불일치하는 문자·수치·각주가 있거나 관계가 모호하면 본문을 유지한다. **요약 전사인 수기 12개는 겹치는 본문을 자동 제거하지 않는다.** 그림 description과 겹치는 본문도 실제 글자와 생성 설명이 다를 수 있어 기본적으로 유지한다.

### 5. 청크 길이와 겹침의 적용 기준

| 설정 | 현재 기준 | 적용 조건 |
| --- | --- | --- |
| 단위 | 문자 수 | 공백 포함. 토큰 수가 아니며, 검색용 텍스트의 Python `len(text)`로 측정 |
| 청크 상한 | 500자 | 제목·반복 헤더·겹침을 포함. 별도 저장하는 ID·좌표·원본 HTML 태그는 제외 |
| 최소 길이 | 없음 | 내용이 완결되면 짧게 둔다. 길이를 채우려고 다른 기능을 합치지 않음 |
| 일반 분할 | 문장·단계 경계 | 다음 문장을 넣으면 상한을 넘을 때 다음 청크로 넘김 |
| 긴 문장 분할 | 구절 → 단어 경계 | 사용할 수 있는 글자 수보다 문장 하나가 길 때 적용. 소수점·모델 번호를 문장 끝으로 오인하지 않음 |
| 일반 겹침 | 마지막 완전한 문장, 최대 100자 | 같은 내용의 연속 청크에만 적용. 마지막 문장이 100자보다 길면 생략 |
| 긴 문장 분할 시 겹침 | 끝 구절, 최대 100자 | 구절·단어 경계를 유지한 범위에서만 반복 |
| 표 | 행 단위 분할 + 헤더 반복 | 무조건 앞 행을 중복하지 않는다. 긴 셀은 행 이름·열 이름을 유지하며 설명을 나눔 |
| 그림 | 그림 하나의 설명이 기본 | 긴 설명만 문장 단위로 분할하고 같은 그림 ID 유지 |

줄바꿈은 `\n` 한 글자로 통일해 세고, 원본의 의미 없는 연속 공백은 검색용 텍스트에서 정리한다. 원본 문자열과의 대응 범위는 별도로 남긴다. 각 청크에 새 내용이 반드시 들어가도록 하며, 겹침 때문에 다음 완전한 문장이 들어가지 못하면 겹침을 줄이거나 생략한다. 제목이나 헤더 자체가 매우 길거나 단일 식별자를 안전하게 나눌 수 없으면 원문을 보존하고 길이 예외로 기록해 검수한다. 단어·숫자를 조용히 잘라 버려 상한을 맞추지 않는다.

500자는 500토큰이 아니다. 임베딩 모델의 실제 입력 제한은 별도로 토크나이저로 확인한다. 48페이지 샘플은 최대 500자·241토큰이었고 검색 결과는 [별도 보고서](reports/RAG_SAMPLE_20261026.md)에 기록했다. 전체 데이터에서 이 길이가 최적이라는 검증은 아니다.

**참고: 이전 토큰 길이 측정 기록**

2026-10-26 실제 토큰 길이도 측정했다. 모델 추론 없이 공식 토크나이저 파일만 사용했으며, train 7,004페이지를 읽었다. `add_special_tokens=False`, 자르기 없음, QA 미사용 조건이다. 표는 현재 HTML의 보이는 셀 텍스트에 구분자를 붙여 측정했고, 병합 헤더를 풀거나 반복 제목을 추가하기 전의 길이다.

| 측정 대상 | 비어 있지 않은 항목 수 | 중앙값 | 95백분위 | 600토큰 이내 |
| --- | ---: | ---: | ---: | ---: |
| 본문 영역 하나 | 103,337 | 12 | 66 | 99.99% |
| 페이지의 원문 본문+제목 | 7,000 | 293 | 654 | 92.73% |
| 그림 description 하나 | 16,202 | 46 | 153 | 100% |
| 표 전체의 보이는 셀 텍스트 | 1,770 | 101 | 420 | 98.25% |

원문 본문+제목 측정에는 그림 description과 새 표 HTML이 포함되지 않았다. 비어 있는 본문 영역·페이지는 해당 길이 통계에서 제외했다. 표 수치에는 train의 수기 보강 표도 포함한다. 현재 저장된 추출문을 측정한 것이므로 추출 누락 여부나 의미 정확도를 증명하지 않는다.

이 측정 때는 목표 400토큰·일반 상한 600토큰을 제안했다. 이후 사용자가 500자를 선택하여 현재 규칙은 위의 글자 수 기준으로 변경했다. 위 측정 수치를 500자 청크의 적합성이나 검색 성능 검증 결과로 해석하지 않는다.

측정 기록은 로컬 `.runtime/pm209-token-length/profile.json`, 재현 스크립트는 같은 폴더의 `profile_lengths.py`다. 공식 토크나이저 리비전은 `97b0c614be4d77ee51c0cef4e5f07c00f9eb65b3`이다. 전체 임베딩·벡터 DB 적재는 실행하지 않았다. [Qwen 공식 모델·토크나이저](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B)

| `title`, `text`, `char_count`, `overlap_char_count`, `token_count` | 검색용 문맥·내용, 글자 수·겹침 글자 수·모델 입력 토큰 수 |
| `content_origin`, `quality_flags` | 원문 / 생성 그림 설명 / Paddle 표 / 수기 요약, 검수 필요·배치 불확실 등의 표시 |

`manual_id`는 확인된 `image_filename` 경로 규칙과 메타데이터 매핑을 사용한다. 페이지 ID 문자열을 임의로 잘라 제품을 추정하지 않는다. `source_shapes`는 여러 영역 좌표의 목록으로 두고 하나의 큰 사각형만으로 합치지 않는다.

본문 영역 일부만 들어간 청크를 검색했다고 해당 영역의 모든 사실을 찾았다고 평가하지 않는다. 반복 제목만으로 검색된 결과 역시 본문 근거를 찾은 것과 구분한다. 이 때문에 직접 내용과 문맥의 영역 ID를 나눈다.

### 7. 검색 뒤 페이지 문맥을 사용하는 방법

검색은 매뉴얼 전체의 청크에서 수행한다. 선택된 청크는 `page_id`로 원래 페이지를 찾을 수 있다. 답변에 추가 문맥이 필요하면 같은 제목 아래의 이웃 문단이나 표의 전체 HTML을 제한적으로 가져온다. 한 청크가 검색됐다는 이유만으로 그 페이지의 모든 그림을 답변에 붙이지 않는다.

페이지 문맥을 보존한다고 반드시 페이지를 먼저 검색하는 2단계 검색기를 구현하는 것은 아니다. 초기안은 **청크 검색 → 필요한 페이지/이웃 문맥 확인**이다. 여러 페이지에서 근거를 가져올 수 있게 두고, 근거가 되는 그림·표 ID만 답변 표시와 연결한다.

### 8. 규칙 확정 전 비교할 것

첫 샘플은 train에서 배치만 보고 고른다. 본문·다단 배치가 많은 매뉴얼, 표가 많은 매뉴얼, 그림·절차가 많은 매뉴얼을 하나씩 골라 청크를 확인한다. QA 정답을 보고 청크 경계를 맞추지 않는다.

| 비교안 | 목적 |
| --- | --- |
| A. 페이지 기준 | 같은 보강 내용을 페이지 단위로 검색하는 기준선. 긴 페이지는 입력 한도를 넘긴 사실과 처리 방식을 기록 |
| B. 영역 기준 | 제목을 붙인 영역 하나씩 검색하여 짧은 청크의 영향을 확인 |
| C. 이번 초안 | 관련 본문을 묶고 그림·표 구조를 살린 청크를 검색 |

세 방법은 같은 보강본·임베딩 모델·매뉴얼 검색 범위를 사용한다. 검색된 청크 수만 같게 하는 비교와 함께, **답변에 전달하는 총 토큰 예산을 같게 하는 비교**도 기록한다. A는 원 논문의 URA 재현 실험이 아니다.

확인 항목:

- **청킹 자체:** 내용 누락, 제목 오연결, 다른 열 혼합, 표 헤더·단위 손실, 중복, 길이 예외, 추적 불가능한 원본 ID 수.
- **페이지 검색:** 청크를 페이지별로 모아 중복을 제거한 뒤 상위 1·3·5페이지의 정답 근거 페이지 포함 여부. 초기 페이지 점수는 해당 페이지 청크의 최대 유사도로 정의하고 고정한다.
- **영역 검색:** 검색 청크의 `content_region_ids`와 QA의 `answer.relevant`를 비교한다. 큰 청크가 여러 영역을 담아 유리해지는 효과를 보기 위해 영역 재현율과 정밀도, 전달 토큰 수를 함께 기록한다. 영역 일부만 포함한 결과는 사실 수준 정확도와 구별한다.
- **다중 페이지 질문:** QA가 기록된 페이지뿐 아니라 `answer.relevant`가 가리키는 실제 페이지를 전역 영역 ID 매핑으로 찾는다. 참조를 해석하지 못하는 항목은 별도로 집계한다.
- **언어:** 먼저 제공된 영어 질문으로 검색을 평가한다. 한국어 질문 평가는 별도 번역·검토 표본으로 구분한다.
- **분할:** train에서 규칙을 개발하고 val로 선택한다. test QA로 경계·길이·검색 개수를 튜닝하지 않는다. 평가 대상 매뉴얼 원문을 검색 자료로 적재하는 것과 정답을 검색 자료에 섞는 것은 구분한다.

이 비교를 보기 전에는 최적 청크 크기나 검색 정확도를 확정하지 않는다. 다음 구현 작업의 첫 산출물은 벡터 DB가 아니라 **샘플 청크 목록과 원본 연결 검수 화면**으로 잡는다.

## 평가 구분

- 그림 설명은 원본과 비교해 글자·숫자·관계·누락·추측을 확인한다.
- 검색·최종 그림 선택은 후속 단계에서 질문별 `answer.relevant`와 대조한다. 이 필드는 모든 본문·그림 연결 관계의 정답지는 아니다.
- 텍스트 답변 정확도는 그림 첨부 여부와 별도로 확인한다.
- train·val에서 조건을 정하고 test는 최종 평가에 사용한다. QA 정답과 근거 표시는 검색용 본문에 넣지 않는다.
