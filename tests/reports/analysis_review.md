# PP-StructureV3와 PaddleOCR-VL: 8GB 장비 실험 결과

실험일: 2026-10-14. 같은 B2B 매뉴얼 42페이지를 수동 보정 없이 분석했습니다.

**새 8GB 설정으로 두 GPU 구성 모두 42페이지를 완료했습니다. 선택한 본문·정형 표 검사에서는 VL이 더 잘 보존했지만, 작은 화면 캡처의 오인식과 번호·읽기 순서 문제는 남았습니다.** 현재 결과를 운영 RAG에 자동 반영하지 않았습니다.

이후 별도 RAG 프로필로 연결해 검색·답변을 실행했습니다. 파싱 결과와 RAG 품질을 구분한 후속 결과는 [VL RAG 검증 보고서](rag_vl_review.md)에 있습니다. 기존 기본 코퍼스는 유지합니다.

페이지별 원문 출력은 [비교표](comparison.md), 자동 점검 원자료는 [analysis_checks.json](analysis_checks.json), 자원 사용 요약은 [resource_summary.json](resource_summary.json)에 있습니다.

2026-10-15에는 경량 모델을 제외하고 Structure·VL의 대표 화면 캡처 7개와 지정 문자열 35개를 추가 평가했습니다. 추출 이미지 보존·JSON 텍스트·Markdown 전달을 구분한 [이미지 평가 보고서](image_evaluation.md)에 정답 작성 방법, 현재 VL의 이미지 OCR 비활성화 설정, 표본과 지표의 한계를 기록했습니다. 모델은 재실행하지 않았습니다.

## 1. 비교한 구성

| 구분 | 주요 구성 | 입력 폭 | 완료 | 보정 전 청크 |
|---|---|---:|---:|---:|
| L: 기존 CPU 경량 | PP-DocLayout-S, 영어 mobile OCR, SLANet_plus | 2,000px | 42/42 | 59 |
| S: 새 GPU Structure 후보 | PP-DocLayout_plus-L, PP-DocBlockLayout, server OCR, SLANeXt 유선·무선 모델 | 1,200px | 42/42 | 44 |
| V: GPU PaddleOCR-VL-1.6 | PP-DocLayoutV3 + VL-1.6-0.9B, native Paddle 실행 | 1,200px | 42/42 | 55 |

S·V는 같은 RTX 5060 Laptop GPU에서 순서대로 실행했습니다. L은 과거 CPU 결과입니다. L과 새 결과에는 장비·모델·언어 지원·입력 해상도 차이가 있으므로 단일 모델의 효과만 분리한 실험이 아닙니다. S는 큰 모델을 사용하는 후보이며 최적 구성이라는 뜻은 아닙니다.

모든 청크는 같은 `split_page()` 규칙으로 생성했습니다. 번호가 Markdown에 어떻게 남는지, 표가 포함되는지도 청크 수에 영향을 줍니다. 청크 수와 HTML 속성을 포함한 글자 수를 정확도 점수로 해석하지 않습니다.

## 2. 실제 환경과 8GB 설정

| 항목 | 확인한 값 |
|---|---|
| GPU / VRAM | RTX 5060 Laptop GPU / 8,151 MiB |
| 시스템 RAM | Windows 보고값 약 23.4 GiB |
| 드라이버 / Paddle CUDA 빌드 | 610.47 / CUDA 12.9 |
| Python / 패키지 | Python 3.10.11, paddlepaddle-gpu 3.3.1, paddleocr 3.7.0, paddlex 3.7.2 |
| 두 구성의 페이지 폭·배치 | 1,200px / 1 |
| VL 영역 최대 픽셀·생성 토큰 | 262,144 / 2,048 |
| Paddle GPU 할당자 상한 | 6,144 MiB, auto_growth |
| 별도 중단 기준 | 장치 GPU 사용량 7,168 MiB 초과, 가용 RAM 2,048 MiB 미만, GPU 온도 80도 이상 |
| VL 가중치 준비 | CPU에서 읽기·정밀도 변환, 최종 모델은 GPU에 배치 |

코드에 16GB를 할당하는 값은 없었습니다. 기존 실행에는 별도 GPU 할당자 상한이 없었고 페이지 폭 2,000px, VL 기본 영역 최대 1,003,520픽셀·4,096토큰을 사용했습니다. 기존 배치도 이미 1이었습니다.

기본 VL 로딩은 5GB와 6GB 상한 모두에서 MemoryError로 정상 중단됐습니다. CPU 체크포인트 준비를 적용한 뒤 같은 6GB 상한에서 표본과 전체 분석을 통과했습니다. `native_cpu_loader.py`는 고정된 PaddleX 3.7.2의 두 로더 함수를 초기화 중에만 임시로 감싸고 복구합니다. 설치 패키지 파일과 캐시 가중치는 수정하지 않았으며 학습·파인튜닝도 하지 않았습니다.

작은 텐서로 CPU 변환의 값·BF16 정밀도 보존과 함수 복구를 확인했습니다. 실제 모델의 모든 파라미터가 GPU에 있는지도 검사했습니다. 파라미터에는 FP32와 BF16이 함께 있으며 전체 모델을 강제로 반정밀도로 바꾸지는 않았습니다.

원래 발생했던 두 시스템 재부팅은 Windows HYPERVISOR_ERROR였으며 근본 원인을 덤프로 확정한 것은 아닙니다. 낮춘 입력과 CPU 로딩을 함께 적용한 이번 실행에서는 추가 재부팅·자원 감시 중단이 없었습니다.

페이지 시간은 렌더링·추론·결과 저장을 포함하며 초기화·다운로드·실행 전 import와 페이지 사이 캐시 정리 시간은 별도입니다. 표본의 1·9·37페이지를 전체 실행에서 재사용했으므로 시간 합은 두 실행에 걸쳐 저장된 42페이지 기록입니다. 첫 페이지들에는 예열·지연 모델 로딩이 포함될 수 있습니다. 반복 측정한 정식 속도 벤치마크는 아닙니다.

자원 수치는 성공한 표본과 전체 실행의 1초 간격 관찰값입니다. 순간 최대 사용량을 보장하지 않습니다. Paddle 할당자 상한과 드라이버·런타임 등을 포함하는 장치 전체 사용량은 다릅니다. 비교에는 5GB·6GB 기본 로딩 실패 로그를 합산하지 않았습니다. 중단·실패 원자료는 폴더 정리 시 삭제했고 성공한 실행의 기록을 보존했습니다.

### 작은 화면 캡처는 별도 실패 영역

37~39페이지의 정형 표 168셀 일치만으로 VL의 모든 표가 정확하다고 결론 내릴 수 없습니다.

- 23페이지 화면 캡처에서 원본의 UPDATE DATE는 `2026-09-01`인데 V 표는 `2020-08-01`로 출력합니다. 실제 헤더 대신 `Questionnaire` 같은 잘못된 이름도 반복됩니다.
- 22페이지 화면 캡처의 Raw Data 필드명도 V에서는 숫자·좌표처럼 보이는 값으로 바뀝니다. 이 영역을 신뢰할 수 있는 원문으로 취급하지 않습니다.
- S 역시 작은 캡처를 깨진 텍스트·표로 만들었습니다. 기존 L이 이런 영역을 이미지로 남긴 경우도 있습니다. 더 많은 텍스트가 나왔다는 사실은 정확한 정보를 더 많이 얻었다는 뜻이 아닙니다.

낮춘 해상도와 작은 원본 캡처는 해석에 영향을 줍니다. 이 실험만으로 모델의 모든 문서·언어·해상도에서의 우열을 일반화하지 않습니다.

## 6. 현재 결론과 다음 실험

1. **실행:** 체크포인트 CPU 준비, 입력·토큰 제한, 할당자 상한과 자원 감시를 적용해 이 8GB PC에서 두 구성의 전체 분석을 완료했습니다. 같은 PC가 앞으로 모든 입력에서 안정적이라는 보장은 아닙니다.
2. **문서 품질:** 이번 선택한 본문과 정형 표에서는 V가 더 잘 보존했습니다. S는 빠르지만 낮은 해상도에서 표 구조와 OCR 오류가 커졌습니다. 기존 영어 경량 결과가 더 나은 사례도 있습니다.
3. **출력 구조:** 두 새 구성 모두 번호·헤딩·읽기 순서 문제가 남았습니다. 특히 V의 37페이지 범례는 인식 이후 필터링에서 사라졌습니다.
4. **RAG:** 운영 코퍼스 73개와 보정 기록은 유지했습니다. 작은 캡처의 잘못된 텍스트가 포함되어 있어 새 결과를 바로 교체하지 않았습니다. 문서 분석 개선이 답변 개선으로 이어졌다고 아직 주장하지 않습니다.

후속 실험은 한 번에 한 조건만 바꾸는 것이 좋습니다. 예를 들어 같은 메모리 상한을 유지한 채 입력 해상도를 조정하거나, 영어·한글 인식기만 바꾸거나, `footer` 필터링만 바꿉니다. 결과는 별도 폴더에 저장합니다. RAG 비교는 같은 청킹·BGE-M3·Qwen·질문 10개와 별도 인덱스를 사용하고 검색·답변 평가를 나눠 진행합니다.
